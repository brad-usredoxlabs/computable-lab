## Design

**D1 — Identity & gating (the coexistence decision).** The URL stays a RUN-record id
(`/runs/RUN-…`, kind run). `GcRunSheetSection` mounts only after RunWorkspacePage's existing
`getRecord` resolves `payload.kind === 'run'`, then ONE probe:
`listRecordsByKind('instrument-sequence', 500)` and keep sequences whose `runRef.id === runId`
(or whose `entryRefs` entries' runRef matches — entries carry the REQUIRED runRef [F schema :21]).
Zero matches → render NOTHING (DNA runs byte-identical, bait #2). [I] Chosen over URL-on-ISEQ
because `/runs/:runId`'s entire server half (workspace/analysis-bundle/ai-context) kind-gates to
`run` [F-run 404 probe] — putting an ISEQ id there would render a shell whose every API call 404s.
The entry `runRef` is REQUIRED by schema, so entry-side linking is schema-guaranteed; header
`runRef` is optional, so the probe checks BOTH header.runRef and resolves entryRefs' runRef.
Open to orch override — OQ-1.

**D2 — Creation flow (front door).** Where no sequence links a run, GC chrome shows ONE action:
"New GC run sheet" — a small form (title, instrument select from `equipment` kind, study optional)
that mints in order via existing `createRecord`: optional run record (quickCreateRun precedent
[F]) if none chosen, entries ISEN-* (position/vial + sample + method refs), header ISEQ-*
(entryRefs + runRef) LAST, mirroring GC-4's create-last discipline. Refs are minted by the
caller (schema ids are caller-supplied patterns; see GC-3 fixtures [F]). No server route needed.
