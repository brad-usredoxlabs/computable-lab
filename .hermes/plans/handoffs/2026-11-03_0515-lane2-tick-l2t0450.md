## THE FINDING — why coders die on appliance-2 (measured, not inferred)

Both recent coder deaths ("inference request expired while waiting for admission") are the engine's
`HTTP 503 | request queue timeout`, and the engine journal shows the shape exactly:

```
06:10:57 / 06:11:30 / 06:12:05Z   WARN req#8616/8617/8618 failed | HTTP 503 | request queue timeout
06:12:23Z                          INFO req#8615 done | output limit | prompt 122,376 | output 32,768 | 2m47.6s
09:27:56Z                          INFO req#9145 done | output limit | prompt 137,838 | output 32,768 | 3m47.2s
09:30:32 / 09:31:05 / 09:31:41Z   WARN req#9163/9164/9165 failed | HTTP 503 | request queue timeout
```

A coder turn that runs to the 32,768-output cap holds the engine's only decode slot for ~3 minutes
(14 such turns between 01:01 and 09:27 UTC). Live coder prompts measure **122K-152K tokens** against
`--kv-capacity 262144 --max-context 262144 --max-concurrency 2`, and `--pending-timeout-ms` is
**unset** on the running cmdline, so admission gives up after ~30 s (derived from the 33 s / 36 s
spacing of the 503 triplets). Two long-context coder sessions therefore cannot co-serve: the second
queues past the timeout, retries three times, and the run dies — which is precisely what happened
8 seconds before each of lane 2's two deaths.

Evidence doc (committed to trunk): `.hermes/plans/2026-11-03_0500-L2-appliance2-coder-serialization-
evidence.md`. Scope stated honestly there: I enumerated every 503 in the journal since 2026-11-02T00Z
(four bursts) and reconstructed who was live for the two that killed lane-2 runs; I did not
reconstruct the 00:07 burst, so "serial ⇒ no 503" is *supported*, not proven.
