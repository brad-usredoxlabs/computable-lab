# FAME-4G — analysis run lists are reachable and honest (lane 1 platform item)

SPEC — orchestrator-authored from the architect ruling
`.hermes/plans/2026-11-01_fame-4g-platform-render-decision.md` (FAME-4G RULED, Option 3).
The ruling IS the approved scope; this spec adds verified cites, file ownership, acceptance.

## Why

The FAME-4 browser gate (receipts/FAME-4/gate-l1t1855/report.md, VERDICT: fix) proved two
reachability defects: `GET /api/analysis-runs` caps at the OLDEST 50 runs and misreports
`total = runs.length`, and the `/analysis?run=<id>` deep link silently no-ops when the run is
not in the loaded page. Newer runs (ANR-000055/056, FAME-5's ANR-000057..060) are unreachable
from the UI. The architect ruled this ONE defect: reachability + honest total. NOT a capability
gap — `GET /api/analysis-runs/ANR-000055` returns 200 with the full outputManifest and the
/analysis ViewRenderer already renders those table views for reachable runs.

## Obligations (verbatim scope from the ruling)

1. SERVER: `AnalysisHandlers.listRuns` (routes.ts:1281, GET /api/analysis-runs) honours
   `limit`/`offset` query params — reuse the `TreeHandlers.listRuns` parse pattern
   (TreeHandlers.ts:1683-1687: `limit ? parseInt(limit,10) : default`, offset default 0).
   `RecordFilter` already supports `limit` and `offset` (server/src/store/types.ts:72,74).
   Returns NEWEST-FIRST: the default page must contain the newest runs. Sort by `updatedAt`
   desc (TreeHandlers precedent) or by numeric id suffix — coder's choice; acceptance only
   requires the newest runs land in the default page.
   Verified first-hand cites: `AnalysisHandlers.ts:87-90` currently ignores the request
   (`_req`) and calls `service.list('analysis-run')`; `analysisService.ts:240` is
   `async list(kind, limit = 50)` returning `store.list({kind, limit})` — scan order
   (recordId order = oldest-first) truncated, so the client only ever sees the oldest 50.
2. SERVER: `total` must be the TRUE count of kind=analysis-run records, never `runs.length`
   (the current misreport at AnalysisHandlers.ts:89 is explicitly in scope — it is what made
   the cap invisible). A count path exists or is trivially derivable from the store; do not
   load all records to count if the store exposes a cheaper way, but correctness beats
   cleverness.
3. CLIENT: the `?run=` deep link resolves by FETCHING the run by id
   (`GET /api/analysis-runs/:id` exists, routes.ts:1283, returns 200 for any run) instead of
   gating on list membership (`AnalysisPage.tsx:300`
   `if (!runs.some((r) => r.recordId === deepLinkRun)) return`). Keep the one-shot
   `deepLinkDoneRef` discipline and the param strip; the `selectRun(deepLinkRun)` landing
   (shared landing + client-side manifest seed, FIX2 M1) is reused verbatim. The effect must
   no longer wait on `runs.length === 0` to fire for a deep link.

## Routine implementation notes (coder may resolve differently within the boundary)

- `service.list` may need an offset param and/or a sort; keep the signature additive so other
  callers (analysis-revision list) are unchanged in behavior.
- Response shape `{ runs, total }` must stay compatible with the client's fetch.
- If the client run-list page has a fixed client-side fetch size, the newest-first server
  default must make the newest runs visible without pagination UI (pagination UI is OUT of
  scope; the acceptance is reachability + honesty).
